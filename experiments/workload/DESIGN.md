# Workload generator: design note

`Generate(Scenario, seed) Workload` describes one round: each shard's build size and DDL arrival, and each shard's finite query stream. The contract is `workload.go`. This note covers the modeling choices that the roadmap and the contract leave open. The generator was written without reading the scheduler, shard or worker code, so nothing in it is tuned to a policy.

## How queries are made

In a sharded database the coordinator either routes a query to the one shard that holds its shard key, or splits it across several shards and merges the results (scatter-gather). Citus calls these *router* and *parallelized* queries [1]. A vector kNN search without a routing key goes to every shard: each shard returns its local top k, and the coordinator merges them [2]. Cluster-wide DDL such as `CREATE INDEX` on a distributed table runs on every shard [1]. That is the round's DDL. Other DDL can run on one shard alone.

So the generator draws **coordinator-level queries** and splits each one into shard pieces:

1. Cluster-query arrivals form one Poisson process at `ClusterQueryRate` over `[0, Horizon]`.
2. Each cluster query draws `NeedsIndex`, which is the same for all its pieces. It also draws a duration factor shared by all its pieces.
3. With probability `FanOutFraction` the query fans out. It picks a width k uniformly from `[FanOutShardsMin, FanOutShardsMax]`, picks k distinct shards uniformly, and sends one piece to each. All pieces have the same `ClusterQueryID` and `Arrival`. Otherwise the query goes to one shard, chosen uniformly, or with the hot shard weighted by `HotShardRateMultiplier`.
4. Separately, each shard gets local DDL: a Poisson process at `LocalDDLRatePerShard` with long durations and `NeedsIndex = false`.
5. Each shard's queries are stable-sorted by arrival. Cluster-query IDs are 1, 2, 3, ... in generation order.

## Modeling choices

| Choice | Alternative | Why | Reference |
| --- | --- | --- | --- |
| Arrivals are **Poisson at the cluster level**. Shard streams come from splitting, so pieces of one query are correlated by construction. | An independent Poisson stream per shard | The owner asked that shard queries not be unrelated. In a sharded system the coordinator receives the load and the shards see its pieces. Open-loop Poisson is the usual default, and the roadmap's model (decision 30) has no client think-time to model. | Citus router vs parallel [1]; YCSB open-loop target throughput [3] |
| Piece CPU duration is **log-normal**, mean `MeanQueryDuration`, σ = 1.0 (CV ≈ 1.3), capped at 20× the mean | Exponential; Pareto | Heavy-tailed but with finite variance, so mean load is controllable and the sweep "arrival rate × duration" means what it says. The cap is hit with probability about 2e-4 and keeps a single draw from dominating a 30 s round. | General OLTP latency practice; no vendor publishes a distribution |
| **Fan-out piece durations are correlated**: log d = μ + 0.8·Z_query + 0.6·Z_piece | Independent pieces; identical pieces | Pieces run the same plan and predicate, which explains the shared factor, on different data, which explains the per-piece factor. Since 0.8² + 0.6² = 1, every piece has the same marginal distribution as a single-shard query, so the mean-load calculation holds. Fully independent pieces would understate how alike the work is; identical pieces would hide per-shard data skew. | Scatter-gather per-shard top-k [2] |
| **`NeedsIndex` is drawn once per cluster query**, independent of fan-out vs single | Tie it to kind (every vector search fans out) | The contract defines the fraction "by cluster query". Independence keeps the `needs_index` sweep (0, 0.5, 1) orthogonal to the fan-out mix, so both knobs work at their extremes. A routed vector search exists: a kNN with a tenant or shard-key filter. See open question 1. | ES kNN [2]; Citus multi-tenant routing [1] |
| Fan-out **width is uniform on [Min, Max]**, shards uniform without replacement. Presets use [2, n]. | Always all shards; a two-point mix (2 shards or all) | k = 2 is the TPC-C-like cross-shard transaction: one remote warehouse in New-Order or Payment [4]. k = n is a full scatter-gather (unfiltered kNN, cluster aggregate). Uniform between them covers partial pruning (IN-lists, range predicates) without inventing a shape the contract can't express. | TPC-C remote-warehouse rules [4]; Citus shard pruning [1] |
| `FanOutFraction` = 0.30 by cluster query (0.15 in downstream_heavy) | TPC-C's ~11% | TPC-C's 11% (45% New-Order × 10% + 43% Payment × 15%) is a pure OLTP floor [4]. A vector database also serves unfiltered kNN and analytics, which scatter, so the default sits above TPC-C. At 6 shards about 63% of shard pieces come from fan-out queries; at 50 shards about 92%, because each fan-out averages 26 pieces. downstream_heavy models a tenant-routed workload (Citus multi-tenant), where most queries are router queries. | TPC-C [4]; Citus [1] |
| **Single-shard routing is uniform** across shards (hot shard aside) | Zipfian by key, as YCSB's 0.99 | YCSB-style key popularity is Zipfian, but hash sharding (Citus, Vitess hash vindex) spreads keys across shards, so per-shard load is near uniform. Skew is applied only through the explicit hot-shard knob, so it is visible and controllable. | YCSB request distributions [3]; Citus/Vitess hash distribution |
| **Hot shard**: weight M against weight 1 for each other shard, redistributing a fixed cluster rate | Add extra queries on top of the rate | Keeps `ClusterQueryRate` meaning the cluster rate. The preset solves for the M that gives the hot shard **4×** a typical shard's total CPU load (fan-out pieces included): M = 8.9 at 6 shards, 24.1 at 50. Without this, fan-out pieces would dilute the hot shard at 50 shards and the scenario would vanish. | — |
| Query load is **independent of shard size** | Load proportional to `NVectors` | No published basis for coupling. Independence is the neutral null, and downstream_heavy deliberately separates load from size. See open question 3. | — |
| **Local DDL**: Poisson per shard at 0.005/s, log-normal with mean 2 s, σ = 0.5, capped at 5× the mean; `NeedsIndex = false`; one shard; unique ID | Exponential; none | The owner says rare, long, one shard. 2 s is 100× a query and about a tenth of a 100k build. That is about one per round at 6 shards and about seven at 50. Lower σ than queries because a local DDL's cost is driven by table size, not by a predicate. | Citus/Vitess allow DDL on a single shard or table |
| **Zipf sizes are rank-size**: the shard of rank r gets Max/r^s, clamped at Min, and ranks are assigned to shards by a seeded permutation | i.i.d. draws from a bounded Zipf/Pareto | The exponent then controls skew exactly. At 6 shards largest/median is 1.9, 3.4, 6.3 for s = 0.5, 1, 1.5. i.i.d. draws at 6 shards would make the realised skew vary more from seed to seed than across the sweep. Note: the seed only permutes Zipf sizes, so round-to-round variation comes from the streams. At 50 shards with Min = 10k, all ranks past 20 (s = 1) are clamped to Min. | Zipf rank-size law |
| **Uniform sizes**: integer uniform on [Min, Max] (Min = Max gives equal sizes) | — | Simplest. | — |
| **Bimodal**: round(f·n) heavy shards (at least 1 if f > 0), stratified over [0.8·Max, Max]; the rest uniform on [Min, 2·Min] | i.i.d. mixture | Stratification guarantees the heavy cluster spans its range. With worker memory set to fit 0.9·Max, some heavy builds fit one worker and some don't, in every seed, as the roadmap's Bimodal row requires. | — |
| **Staggered DDL**: stratified uniform. The shard in slot j (seeded permutation) draws from [j·S/n, (j+1)·S/n] | i.i.d. uniform on [0, S] | The spread always covers [0, S] instead of sometimes bunching at 6 shards. Still random per seed. | — |
| **Rates come from a target per-shard utilisation**: R = u·n / (mean·((1−f) + f·E[k])) | A fixed cluster rate | Per-shard load then stays the same at 6 and 50 shards, so the "shard count" sweep compares like with like. The roadmap's "light" and "moderate" become u = 0.15 and u = 0.4. | Roadmap sweep "arrival rate × duration" |
| Mean query 20 ms; Horizon 30 s (40 s staggered) | Sub-millisecond OLTP | The roadmap's cost model makes a 100k × 128 CPU build about 20 s. A 30 s horizon overlaps builds from 1.6 s (10k) to about 42 s (200k). 20 ms is a plausible vector search or small OLTP query. Even with the 10× test speed-up it is 2 ms of sleep, which keeps the number of pieces manageable (about 3.4k at 6 shards, 30k at 50). | Roadmap Phase 1 cost model |
| PCG source `rand.NewPCG(seed, const)`; fixed draw order (sizes, offsets, cluster stream, local DDL by shard) | Global source | Invariant 10. The draw order is documented in `Generate`. | — |

## Presets

All presets: Dim 128, mean query 20 ms, piece σ = 1.0, local DDL 0.005/s/shard at 2 s, fan-out width [2, n], hot shard off unless listed. Workers: 2 below 50 shards, 3 at 50 (roadmap targets). Worker memory: 16 GiB (no limit) unless listed. Rates shown at 6 / 50 shards.

| Preset | Sizes | DDL | Stream | Pool | What it stresses |
| --- | --- | --- | --- | --- | --- |
| `uniform` | uniform [100k, 100k] (all equal) | all at once | u = 0.15 (light): 23.7 / 44.1 q/s, fan-out 0.30, needs_index 0.5, 30 s | 2 / 3 workers | Pure queueing: n equal builds on 2 or 3 GPUs; whether CPU fallback relieves an undersized pool. |
| `skewed` (default) | Zipf s = 1.0, [10k, 200k] | all at once | u = 0.4 (moderate): 63.2 / 117.6 q/s, fan-out 0.30, needs_index 0.5, 30 s | 2 / 3 | Critical-path priority: one build several times the median sets the round. |
| `bimodal` | 25% heavy in [320k, 400k], rest in [10k, 20k] | all at once | as skewed | 2 / 3, **219 MiB** per worker (fits heavy builds up to 360k by the generator's 640 B/vector estimate) | Memory bin-packing (some heavy builds fit no worker and must build locally) and stragglers set by huge builds. |
| `downstream_heavy` | uniform [80k, 120k] | all at once | typical shard u = 0.15; **shard 0 hot at 4× load** (M = 8.9 / 24.1); fan-out 0.15; needs_index 0.8; 46.5 / 83.7 q/s; 30 s | 2 / 3 | The critical path is set by the queries behind one shard's build, not by size; visible only through that shard's reports. |
| `staggered` | as skewed | **staggered over 15 s** | as skewed, horizon **40 s** | 2 / 3 | GPUs idle while CPU builds are mid-flight (speculation, reneging). |
| `shrinking_pool` | as skewed | all at once | as skewed | 2 / 3; the runner removes a worker mid-round | Reneging queued jobs back to local. The workload is identical to `skewed` (same draws for the same seed; only `Name` differs). The worker loss is a runtime event the contract does not describe. |

## Open questions

1. **Should `NeedsIndex` correlate with fan-out?** In a real vector database most index-dependent queries are unfiltered kNN searches that scatter to all shards. I kept them independent so the sweep knobs stay orthogonal. If the owner prefers realism, a contract field such as `NeedsIndexFanOutBias` would express it.
2. **downstream_heavy says the hot shard's queries are "mostly needing the index"**, but the contract has only a global `NeedsIndexFraction`. I set it to 0.8 for every shard in that preset. A per-hot-shard fraction would need a contract field.
3. **Should query load scale with shard size?** If larger shards hold more rows, they may receive more routed queries. Not modeled; it would couple the size and stream knobs.
4. **NeedsIndex queries that arrive before the shard's DDL (staggered).** They are generated like any other query. Does the shard treat them as waiting for the new index (current reading of decision 32), or as runnable because no index was promised yet? The docs don't say.
5. **Memory model.** The bimodal worker memory comes from my own 640 B/vector estimate (float32 vectors plus an M=16 HNSW layer 0). The scheduler's `b × n × dim` constant lives in config I may not read. If b differs, `WorkerMemBytes` should be recomputed so that 0.9·Max is the fit boundary. Exposed as `ApproxBuildMemBytesPerVector`.
6. **Do NeedsIndex and other queries have different durations?** The contract has one `MeanQueryDuration`. A vector search is probably costlier than a point lookup.
7. **Cross-version determinism.** `math/rand/v2`'s PCG is specified, but derived methods (`ExpFloat64`, `NormFloat64`, `IntN`, `Perm`) are not promised stable across Go releases. Byte-identical output is guaranteed for a fixed Go toolchain (go.mod pins 1.27.1). A consumer that stores workloads should store the JSON, not just the seed.
8. **Size of a 50-shard workload.** About 30k to 40k shard queries per round. Fine for the simulator; the live shard simulator must send `POST /jobs` per arrival, which is about 1,000 to 1,300 requests/s at 50 shards (up to about 13,000/s with the 10× test speed-up). Worth checking against the API.
